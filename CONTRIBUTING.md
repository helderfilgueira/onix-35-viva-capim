# Como contribuir

Use issue com objetivo, persona, escopo, critérios de aceite e dependências. Trabalhe em branch curta e abra pull request; descreva comportamento antes/depois, validação realmente executada e limitações. Não marcar teste como aprovado sem evidência.

Preserve `missao-1/` como entrega histórica e `laboratorio/` como autoridade da planta e mapa. O piloto Django fica separado; mudança de geometria deve ser rastreável à fonte. Novas permissões são verificadas no servidor e precisam de teste de acesso cruzado entre organizações.

Cada executor tem um arquivo/área definido; combinar antes de editar o mesmo arquivo. Revisão cobre domínio, interface, privacidade e operação conforme a mudança. Não incluir bancos, dados pessoais, segredos, planta técnica bruta ou screenshots com dados reais.

Definição de pronto: critérios da issue atendidos; testes relevantes executados; migrações revisadas; interface/idiomas verificados se afetados; documentação atualizada; limitações registradas. Um PR aberto, código compilando ou captura bonita não comprova jornada completa.

Responsáveis humanos e agentes estão em [docs/EQUIPE_E_BACKLOG.md](docs/EQUIPE_E_BACKLOG.md). CODEOWNERS indica somente a conta do proprietário já conhecida; outros handles só serão adicionados quando confirmados. Proteções de branch e exigência de review precisam ser configuradas separadamente; este arquivo não as ativa.
